### <a name=""></a>**Детализация синхронизации ставок из АБС**

- Триггер/расписание:
  - Ежедневная пакетная синхронизация в 06:00 по местному времени.
  - Ручной триггер администратором (админ‑эндпоинт) при внеплановых изменениях ставок.
- Канал обмена с АБС: batch через БД/файл и/или REST по расписанию (без онлайн‑нагрузки на БД АБС).
- Идемпотентность:
  - UPSERT по составному ключу: {rateId, asOfDate, productCode, currency}.
  - Для входящих пачек хранить eventId/etag и журнал обработанных событий для дедупликации (at‑least‑once → effectively exactly‑once).
  - Версионирование записей ставок (version, validFrom/validTo) для аудита.
- Политика кэша (Redis):
  - TTL 15 минут для ключей каталога ставок.
  - Политика stale‑while‑revalidate до 5 минут: при истечении TTL отдать последнюю версию и асинхронно обновить кэш.
  - Инвалидация кэша по завершении batch‑загрузки и по ручному триггеру.
- Метрики/алерты:
  - Свежесть данных (age) ≤ 24 часа; алерт при превышении.
  - Ошибки загрузки/дедупликации; длительность job; размер пачки; доля обновлённых записей.

### <a name=""></a>**Решение**
**Логика выбора решения:**

Делаем хорошо, плохо не делаем.

1.  Разгрузка АБС и масштабирование: Главная проблема – перегрузка и вертикальное масштабирование АБС. Решение - разделить монолит/сценарии на микросервисы.
2.  Высокая доступность и Производительность: Введение выделенного сервиса ставок с кэшированием - Redis позволяет предоставлять данные о ставках быстрее.
3.  Асинхронность и Надежность: Для приема заявок из ИБ используется API‑шлюз (HTTPS/JWT, Idempotency‑Key) с публикацией в Kafka через REST Proxy; прямой работы ИБ с Kafka нет из‑за несовместимости платформы. Это обеспечивает надёжную асинхронную доставку заявок в сервис ставок и разгружает АБС.
4.  Технологический стек: Новые сервисы разрабатываются на Java/Spring Boot или .NET Core с использованием PostgreSQL в качестве БД.

### <a name=""></a>**Альтернативы**

Делать плохо, хорошо не делать

1. Интегрировать интернет-банк с API АБС
2. Использовать текущие бд и не выделять сервисы
3. Не использовать асинхронное взаимодействие.

**Недостатки, ограничения, риски**

1. Переход на микросервисную архитектуру увеличивает количество компонентов. Это усложняет мониторинг, развёртывание и поддержку.
2. Потенциально большее latency из-за лишних сервисов
