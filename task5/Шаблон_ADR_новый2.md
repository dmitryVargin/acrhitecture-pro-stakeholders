### **Контракт сообщения «заявка»**

- Топик: `applications.v1`; ключ партиционирования: `clientId` (или `applicationId` при наличии).
- Формат: JSON (application/json), допускается CloudEvents 1.0 в заголовках.
- Схема (версия `1.0`):
```
{
  "eventType": "CreditApplicationSubmitted",
  "eventVersion": "1.0",
  "eventId": "uuid",
  "occurredAt": "RFC3339",
  "producer": "gateway",
  "key": "client-12345",
  "data": {
    "applicationId": "uuid",
    "clientId": "client-12345",
    "channel": "ib|site",
    "fullName": "Строка",
    "phone": "+7...",
    "productCode": "CASH_12",
    "amount": 300000,
    "termMonths": 12,
    "passport": { "series": "....", "number": "...." }
  }
}
```
- Идемпотентность: заголовок `Idempotency-Key` (uuid) + `eventId`; на приёме — запись статуса обработки для ключа на 48 часов.
- Версионирование: `eventVersion` (минорные совместимы; мажор — новый топик `applications.v2`).

### **Доставка и дедупликация**

- Семантика доставки: at‑least‑once.
- Публикация: 10 попыток с экспоненциальной задержкой (100мс, 200мс, …, до 5с); при неуспехе — outbox → фоновый публикатор; крайний случай — DLQ `applications.v1.dlq` + алерт.
- Потребление: идемпотентная обработка в скоринге; хранение `eventId`/`applicationId` в таблице дедупликации ≥ 48 часов; повторные — игнорируются или апсертом.

### **Решение (кратко и согласовано с диаграммами)**

- Центральные компоненты приёма: «API‑шлюз» — фасад (HTTPS+OAuth2, Idempotency‑Key, валидация, rate‑limit); «Сервис заявок на кредит» — доменный сервис (контейнер `application_service`), получает от API‑шлюза и публикует в Kafka (REST Proxy). Терминология согласована с диаграммами.
- «Система кредитного скоринга» — подписчик топика `applications.v1`, делает запросы в БКИ и использует данные АБС (ночная загрузка + on‑demand), пишет только одобренные в Кредитный конвейер.
- «АБС» — источник мастер‑данных; «СМС‑шлюз» — OTP/статусы по SMS API.
- Границы доверия: «Внешние системы» (клиент, БКИ, СМС‑шлюз) и «Внутренний контур банка» (все контейнеры приёма/обработки).

### **Альтернативы (кратко)**

- Прямой ИБ → Kafka (отклонено: несовместимость платформы ИБ; см. FURPS+).
- Синхронный путь в конвейер (отклонено: нет буфера/устойчивости к пикам; высокий риск перегрузки).

### **Недостатки, ограничения, риски**

- Дополнительная сложность (Kafka, шлюз, ретраи, DLQ) требует зрелых runbooks, мониторинга и алертинга.
- Ограничения БКИ (лимиты/стоимость) — важно кэширование и graceful degradation (статус PENDING).
