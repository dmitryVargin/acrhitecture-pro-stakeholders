### <a name=""></a>**Решение**
**Логика выбора решения:**

Делаем хорошо, плохо не делаем.

1.  Разгрузка АБС и масштабирование: Главная проблема – перегрузка и вертикальное масштабирование АБС. Решение - разделить монолит/сценарии на микросервисы.
2.  Высокая доступность и Производительность: Введение выделенного сервиса ставок с кэшированием - Redis позволяет предоставлять данные о ставках быстрее.
3.  Асинхронность и Надежность: Для приема заявок из ИБ используется Kafka, что обеспечивает надежную асинхронную доставку заявок в сервис заявок и разгружает АБС.
4.  Технологический стек: Новые сервисы разрабатываются на Java/Spring Boot или .NET Core с использованием PostgreSQL в качестве БД.

### <a name=""></a>**Альтернативы**

Делать плохо, хорошо не делать

1. Интегрировать интернет-банк с API АБС
2. Использовать текущие бд и не выделять сервисы
3. Не использовать асинхронное взаимодействие.

**Недостатки, ограничения, риски**

1. Переход на микросервисную архитектуру увеличивает количество компонентов. Это усложняет мониторинг, развёртывание и поддержку.
2. Потенциально большее latency из-за лишних сервисов
